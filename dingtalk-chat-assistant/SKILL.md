# 钉钉聊天助手

使用 `dws` 获取当前账号被授权访问的消息，完成可追溯总结和受控智能应答。不要把本技能描述成能读取企业内任意聊天记录，也不要把 Codex 技能描述成常驻消息监听服务。

## 开始前

1. 只使用 `dws` 操作钉钉；不要直接调用 HTTP、Webhook 或浏览器代替 `dws`。
2. 每条 `dws` 执行命令都加 `--format json`。先从查询结果提取 ID，不要猜测 `openConversationId`、`openMessageId`、`userId`、`openDingTalkId` 或 `robotCode`。
3. 命令参数以当前二进制的 `dws <command> --help` 为事实源。参考 [dws-workflows.md](references/dws-workflows.md) 选择命令；帮助与参考冲突时遵循帮助。
4. 总结或拟答时读取 [response-policy.md](references/response-policy.md)；任何发送请求还必须读取 [delivery-policy.md](references/delivery-policy.md)。向产品经理提问、登记问题或接收答复时读取 [question-confirmation.md](references/question-confirmation.md)。设计实时机器人或回答权限、消息类型、接入模式时再读取 [official-docs.md](references/official-docs.md)。
5. 不输出访问令牌、AppKey、AppSecret、Webhook token、完整手机号或无关私人消息。

## 路由请求

按用户描述选择最窄的读取范围：

- 指定群聊：先搜索群并确认唯一结果，再拉群消息。
- 指定某人的单聊：先查得真实用户 ID，再拉单聊消息。
- 指定时间段但未指定会话：拉当前用户在该时间段有权访问的全部会话消息。
- 指定关键词、发送者、会话或 `@我`：使用多维搜索。
- “哪些消息需要回复”：先查未读会话或 `@我`，再逐个拉取必要上下文。
- 遇到需求、设计或验收口径问题，需要产品经理确认：进入问题确认流程；后续“检查答复”从本地登记表恢复问题上下文。

用户只说“最近”时，默认最近 24 小时并在结果开头声明该假设。搜索到多个同名群或同名联系人时，列出候选并等待用户选择，不要自行选取。

## 总结聊天记录

1. 明确时间范围、会话范围和本地时区。记录用户要求的筛选条件。
2. 按 [dws-workflows.md](references/dws-workflows.md) 拉取消息。`hasMore=true` 时使用响应给出的下一游标或边界时间继续；最多先处理 500 条，超过时说明截断范围并询问是否继续。
3. 按消息 ID 去重，按创建时间升序排列。保留发送者、会话、时间、消息 ID、回复关系和话题 ID；把系统通知与人工消息分开。
4. 对含 `openConvThreadId` 的话题主消息继续拉取话题回复，避免把不完整话题直接总结为结论。
5. 按 [response-policy.md](references/response-policy.md) 生成总结。事实、决定、建议和推断必须分开；缺失负责人或截止时间时写“未明确”，不要补全。
6. 报告实际覆盖范围、消息条数、会话数、分页是否完整，以及因权限、消息类型或截断造成的缺口。

## 智能应答

1. 先读取待回复消息及其必要上下文。至少覆盖被引用消息、同一会话紧邻消息和相关历史决定；不要只凭通知摘要作答。
2. 判断消息是否真的需要回复。纯通知、已由他人闭环、无明确行动对象的消息可标为“无需回复”，但说明理由。
3. 按 [response-policy.md](references/response-policy.md) 拟答。不要代用户承诺未确认的时间、预算、交付、权限或立场；信息不足时生成澄清式回复。
4. 按 [delivery-policy.md](references/delivery-policy.md) 核验收件人并判断正文来源。先用 `scripts/apply_watermark.py` 添加可见 AI 水印，再用 `scripts/message_metrics.py` 对带水印的最终正文执行 500 字符分流；不得先计数后补水印。
5. 普通目标先展示预览并获得对当前预览的明确确认；命中可信好友规则时不展示待确认预览，直接执行本次明确发送请求。目标不唯一、身份字段变化或规则不完整时回退到普通确认流程。
6. 只有当前请求明确要求“发送”或“回复”才构成发送意图；可信收件人豁免不能把总结或拟答请求升级为发送请求，也不能移除 AI 水印。
7. 当前用户身份的上下文回复使用 `dws chat message reply`；明确要求机器人身份时使用 `dws chat message send-by-bot`。不要用个人身份冒充机器人，也不要用机器人身份冒充个人。长消息附件仅走当前用户身份支持的文件消息链路，不能静默切换发送身份。
8. 每个可见发送动作使用独立的新幂等 UUID（命令支持时），保存发送响应中的任务键或消息键，并向用户报告实际发送目标、摘要和附件各自的结果。

## 问题确认

1. 先验证问题无法从当前权威资料、既有决定和实现证据中回答，并说明它会影响的实现、测试或交付；避免把一般讨论都升级为产品确认。
2. 按 [question-confirmation.md](references/question-confirmation.md) 唯一解析产品经理，创建问题编号并用 `scripts/question_registry.py` 登记。不得猜测负责人或在登记表中保存完整需求正文。
3. 生成结构化问题，使用 `scripts/apply_watermark.py` 添加 `【AI生成】`，再执行普通投递策略。问题编号必须出现在正文；普通目标需要确认，可信好友豁免保持不变。
4. 发送成功后登记任务键、会话和时间，再回读单聊定位本人发出的关联消息 ID。发送失败时标记失败，不得进入等待状态。
5. 检查回复时按引用关系、完整问题编号、发送者和时间顺序关联。只有强关联且明确回答时标记已答；弱关联或多候选必须标记歧义并让用户判断。
6. 收到答复后区分产品明确结论、适用范围、待办和智能体推断。需要追问时沿用原问题编号并重新走发送策略；需要继续原任务时遵循用户对自动继续的授权。

## 实时机器人模式

当用户要求“收到消息立即自动回复”时，先说明本技能不能常驻监听。按照 [official-docs.md](references/official-docs.md) 设计或实现独立服务：企业机器人接收消息 -> 验签/鉴权与幂等 -> 上下文检索 -> 回复策略 -> 添加可见 AI 水印 -> 钉钉发送接口 -> 审计与人工接管。

默认采用“低风险自动回复，高风险转人工”的策略。涉及人事、财务、法务、客户承诺、敏感数据、权限变更或无法核验事实时，不自动发送。

## 错误处理

- 认证或权限失败时停止并报告缺少的授权，不尝试绕过。
- `unknown command` 或 `unknown flag` 时先运行对应层级 `--help`，仅修正一次。
- 其他失败加 `--verbose` 重试一次；保留相同幂等 UUID。仍失败则停止并报告错误，避免重复发送。
- 未拿到明确成功响应时，不宣称已发送。
